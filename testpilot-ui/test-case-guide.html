How to write a clear test case

This guide is for business users, reviewers and testers who want to add or edit a test case. You do not need programming knowledge. The goal is to describe where the test starts, what the user does, and exactly what should happen.

1. Test case structure

A good test case has four simple parts:

PartWhat it meansExample
TitleOne short sentence describing the scenario.Reject login when username is empty
PreconditionsWhat must already be true before the first action.User is on the login page
StepsActions performed in order.clear username, enter password, click Sign In
Expected ResultsObservable outcomes that prove success or failure.Username error is visible and contains “Username is required.”
Think of a test case as: Given this starting situation → when I perform these actions → then these visible outcomes must occur.

2. Preconditions

A precondition describes the starting situation. It should not describe the action being tested. Write one condition per line.

Good examples

User is on the login page
User is already signed in
Feedback form is open
A customer record already exists
Shopping cart contains one product
User has manager permission
Browser storage does not contain a previous session

Avoid vague preconditions

Avoid phrases such as “System is ready”, “Everything is configured”, or “User can use the page”. Say exactly what page, record, permission or state is required.

Navigation preconditions

User is on /login
User is on https://example.com/feedback
User is signed in and viewing /profile

Data preconditions

A customer with email customer@example.com exists
No account exists for newuser@example.com
Product ABC-100 is in stock
Order ORD-1001 has status Pending

When no precondition is needed

If the test can begin directly from the supplied target URL and has no special setup, you may write:

Start from the application home page

3. Steps

Each step should contain one action. For manual test cases, the recommended format is:

action | target | value

The value is required only when the action needs one.

ActionWhen to use itExample
fillEnter text or a number.fill | [data-testid="email"] | user@example.com
clearMake a field intentionally empty.clear | [data-testid="username"]
clickClick a button, link or element.click | [data-testid="login-button"]
selectSelect an option.select | [data-testid="country"] | Oman
checkTurn a checkbox on.check | [data-testid="terms"]
uncheckTurn a checkbox off.uncheck | [data-testid="newsletter"]
navigateOpen another application page.navigate | /feedback
keypressPress a keyboard key.keypress | [data-testid="search"] | ENTER
Important for empty-field tests: do not write fill | username | with no value. Use clear. This explicitly means “leave this field empty”.

Targets

A target identifies the page element to use. If the application provides a stable test identifier, prefer it:

[data-testid="username"]
[data-testid="submit-feedback"]
[data-testid="age-error"]

If you do not know the target, describe the action in plain language while creating the scenario with AI, or ask a reviewer who knows the application. Avoid inventing technical identifiers.

Step-writing rules

Keep actions in the same order a real user would perform them. One line = one action. Do not put expected outcomes such as “error message is visible” in Steps; those belong under Expected Results.

4. Expected Results

An expected result must describe something observable. Write one expectation per line. Be specific about the element, text, value, page, count or state.

What you want to verifyRecommended wording
Element is visibleElement [data-testid="username-error"] is visible
Element is not visibleElement [data-testid="loading"] is hidden
Exact textText in [data-testid="username-error"] equals "Username is required."
Text contains phraseText in [data-testid="message"] contains "Welcome"
Field valueValue in [data-testid="email"] equals "user@example.com"
Field emptyValue in [data-testid="search"] is empty
Enabled/disabledElement [data-testid="save-button"] is disabled
Checked/uncheckedElement [data-testid="terms"] is checked
Page addressURL contains "/dashboard"
Page titlePage title contains "Dashboard"
Item countElement [data-testid="result-row"] count equals 5
Required fieldElement [data-testid="email"] is required
Invalid fieldElement [data-testid="email"] is invalid
Response statusResponse status equals 200
AccessibilityNo accessibility violations are present
Do not mix message text with field state. “Text contains ‘Account is disabled’” means verify the message text. “Element is disabled” means verify that the control cannot be used. These are different checks.

Prefer evidence over vague outcomes

Too vague
Login should fail.
Form should work.
Correct error is shown.
Page looks fine.
Better
Element [data-testid="login-error"] is visible.
Text contains “Invalid username or password”.
URL remains on /login.

7. FAQ

Do I need to know programming?No. Write the business scenario clearly. The structured step format helps the system understand exactly what action and target you mean.
Can I write plain sentences in Preconditions?Yes. Preconditions are intentionally human-readable.
Why does an empty field use “clear” instead of “fill”?“Clear” explicitly says the intended test state is empty. A fill action normally expects a value to enter.
Where should I write “error message is visible”?Under Expected Results, not Steps.
Can I have more than one expected result?Yes. Add one observable expectation per line. A test can verify visibility, text and navigation together.
What if I do not know an element target?Use AI-assisted creation or ask a reviewer familiar with the page. Do not guess technical identifiers.
What does “Automation Ready” mean?It means the test is clear and grounded enough to execute. It does not mean the application will pass the test.
Can a failed test case be edited just to make it pass?No. Keep the approved business requirement intact. Change the test only when the test itself is incorrect or incomplete.

8. Quick checklist before saving

✓ The title describes one scenario.
✓ Preconditions describe only the starting state.
✓ Each step contains one action.
✓ Empty fields use clear.
✓ Expected results contain observable evidence.
✓ Error-message text is written as a text expectation.
✓ Test steps do not contain verification/assertion instructions.
✓ Negative tests do not weaken the business requirement just to pass.
