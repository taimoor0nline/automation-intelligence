3. Preconditions

Describe what must already be true. Do not put the main action being tested here.

User is on the Login page.
User is signed in as a Manager.
Feedback form is open.
A customer record already exists.
Order ORD-1001 has status Pending.
Avoid vague statements such as “System is ready” or “Everything is configured”. State the actual page, user state, data or permission required.

4. Steps — Human View

Write one recognizable user action per line. Users do not need to write technical execution syntax.

1. Enter 17 in the Age field.
2. Click Submit Feedback.
1. Leave Username empty.
2. Enter TestPassword123 in Password.
3. Click Sign In.

Useful verbs include Enter, Leave empty, Clear, Click, Select, Choose, Open, Upload, Search, Check and Uncheck.

Important: “Leave Username empty” is valid human test language. The system is responsible for translating that intention into an executable empty-field action.

5. Expected Results — Human View

Write observable outcomes, one per line where possible.

1. The feedback form is not submitted successfully.
2. An Age validation message is displayed.
3. The message indicates that the minimum permitted age is 18.
4. The user can correct the Age value.
Too vagueBetter
Login should fail.User remains on Login and an invalid-credentials message is displayed.
Correct error is shown.A Username required message is displayed near Username.
Page works correctly.Dashboard opens and the signed-in user's dashboard is visible.
Expected results should be objectively verifiable through visible state, page/navigation state, values, messages, counts, request/response behavior or another observable condition.

DetailWhy it matters
Resolved elementsShows which page control was matched to human wording.
ActionsShows executable operations such as TYPE, CLICK, CLEAR and NAVIGATE.

Technical syntax belongs here for debugging; it is not the required writing format for normal users.

7. Readiness and Repair

Automation Ready means the reviewed case has complete executable actions and verifiable outcomes. It does not mean the application will pass.

Why can wording look unchanged after repair?

The human intention may already be correct while its technical interpretation is incomplete.

Human intention
Leave Username empty.
Before repair — incomplete automation interpretation
TYPE → Username → [missing value]
After repair
CLEAR → Username

The human test did not need to change. The automation representation changed from incomplete to explicit, allowing the case to become Ready.

Transparency requirement: whenever repair changes readiness, Automation Details should show what changed. The user should not have to guess.
Repair History
Before: TYPE → Username → [missing value]
After:  CLEAR → Username
Reason: The test intentionally requires Username to be empty.
Result: Automation Ready

When clarification is required

Human step: Click Submit.
Issue: More than one Submit control was found.
Result: Ask the reviewer which Submit is intended.
Expected result: The page should work correctly.
Issue: No objective outcome can be verified.
Result: Ask what should be visible, change, open or be returned.

10. FAQ

Do I need programming knowledge?
No. Write the Human Test Case naturally.
Do I need selectors or technical identifiers?
No for normal authoring. Automation Details can show the resolved technical element.
Can advanced users see technical syntax?
Yes. Automation Details is specifically for debugging, resolved actions/assertions, grounding and repair history.
Why can a case become Ready while the human wording remains the same?
The human intention may be valid while the technical execution representation needed repair.
Does Automation Ready guarantee PASS?
No. It means executable. PASS/FAIL is determined during execution.
Should I weaken a test to make it pass?
No. If the requirement is correct and the application violates it, the test should fail until the application is fixed.

11. Before saving

□ One clear scenario is described.
□ Preconditions define the starting state.
□ Steps follow real user behavior.
□ Expected results are observable and specific.
□ Boundary/negative data is explicit where relevant.
□ Vague phrases such as “works correctly” are avoided.
□ Automation Details can be inspected when readiness fails.
□ Repair history explains Before, After and Reason.
□ Automation Ready is understood as executable, not guaranteed PASS.
