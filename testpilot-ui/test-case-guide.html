Scenario Type and Test Category are different. A case can be Negative + Security, Boundary + Performance, Positive + API, or Functional + Accessibility.

4. Cyber-security testing helper

Select Security when the scenario verifies a security control. Choose the most relevant Security Subcategory and assign a Severity representing the impact if the control fails.

Security subcategoryTypical test intent
AuthenticationInvalid login rejection, required credentials, logout behavior.
Authorization / RBACA user cannot access a page/action outside the assigned role.
Session ManagementLogout invalidates access; expired/invalid sessions are rejected.
Input ValidationUnexpected or malformed controlled input is safely rejected.
XSS / InjectionRecord and verify safe application handling of controlled validation scenarios without active exploitation.
CSRFVerify expected request/session protection where it can be observed safely.
Security Headers / Cookies / CORSVerify required security attributes and response headers.
Sensitive Data ExposureVerify protected data is not exposed to unauthorized users or ordinary responses/UI.
API Security / Access ControlVerify authenticated/authorized API behavior and rejected unauthorized requests.
File UploadVerify permitted file type/size and application validation rules.
Rate LimitingRecord the control requirement and perform safe bounded functional verification where appropriate.
Error / Information LeakageVerify responses do not expose prohibited diagnostic details.
TLS / TransportPlan, classify and report transport-security requirements.
Logging & AuditVerify expected security events are recorded where audit evidence is accessible.
Dependency Vulnerability ScanPlan, classify and report dependency/SCA requirements or findings.
Security execution boundary: Dependency Vulnerability Scan can be planned, classified and reported, but package/SCA scanning is not part of the normal browser/API execution engine. Active exploitation, password spraying, network attacks, port/network vulnerability scanning and destructive penetration testing are also not part of this engine and must not be represented as executed or passed by it.

5. Automation Ready means executable, not guaranteed PASS

Automation Ready means the reviewed case has complete executable actions and verifiable outcomes supported by the current execution path. It does not mean the application will pass, and it does not mean a capability outside the browser/API engine has been executed.

Do not weaken a requirement to make a test pass. If the requirement is correct and the application violates it, the test should fail and be reported for remediation.

Example of an intentional demo failure

Title: Reject feedback when Age is below the minimum
Scenario Type: Boundary
Category: Functional
Priority: High

Precondition: User is logged in and on the Feedback page.
Steps:
1. Complete all required feedback fields with valid values.
2. Enter 17 in Age.
3. Click Submit Feedback.
Expected Results:
1. Feedback is not submitted successfully.
2. An Age validation message is displayed.
3. The message states that Age must be between 18 and 100.

If the demo application incorrectly accepts Age 17, this test should execute normally but finish as FAIL. That demonstrates the difference between Automation Ready and application correctness.

6. FAQ

Can Security tests run in the existing engine?
Yes for security-functional browser/API controls that can be safely and objectively verified, such as authentication, authorization, session behavior, headers, cookies and controlled validation cases.
Does selecting Dependency Vulnerability Scan scan packages?
No. It can be classified, planned and reported, but package/SCA scanning is outside the normal browser/API execution engine.
Does Security mean penetration testing?
No. Security-functional testing and active penetration/network testing are different disciplines. Active exploitation, password spraying, network attacks and destructive penetration testing are outside this engine.
Can Load or Stress use normal browser execution?
Not for true concurrency, saturation or throughput testing. Those categories can be planned/reported, while the normal browser/API engine performs only its supported execution.
Does Automation Ready guarantee PASS?
No. It means executable. PASS/FAIL is determined during execution.
