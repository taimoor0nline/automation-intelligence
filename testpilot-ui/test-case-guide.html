4. Cyber-security testing helper

Select Security when the purpose of the scenario is to verify a security control. Then choose the most relevant Security Subcategory and assign a Severity representing the security impact if that control fails.

Security subcategoryTypical safe test intent
AuthenticationInvalid login rejection, required credentials, logout behavior.
Authorization / RBACA user cannot access a page/action outside the assigned role.
Session ManagementLogout invalidates access; expired/invalid sessions are rejected.
Input ValidationUnexpected or malformed input is safely rejected.
XSS / InjectionVerify application handling of controlled test input without destructive exploitation.
CSRFVerify expected request/session protection where observable.
Security Headers / Cookies / CORSVerify required security attributes and response headers.
Sensitive Data ExposureVerify protected data is not exposed to unauthorized users or ordinary responses/UI.
API Security / Access ControlVerify authenticated/authorized API behavior and rejected unauthorized requests.
File UploadVerify permitted file type/size and application validation rules.
Rate LimitingRecord the control requirement and perform safe bounded functional verification where appropriate.
Error / Information LeakageVerify user-facing responses do not expose prohibited diagnostic details.
TLS / TransportRecord and report transport-security requirements; specialist scanners provide protocol/cipher assessment.
Logging & AuditVerify expected security events are recorded where audit evidence is accessible.
Dependency Vulnerability ScanPlan, classify and report dependency/SCA findings.
Engine boundary: Dependency Vulnerability Scan can be planned, classified and reported in AI TestPilot, but the normal browser/API execution engine does not perform package/SCA scanning, active exploitation, password spraying, network attacks, port/network vulnerability scanning or destructive penetration testing. These are separate security-engine capabilities and should not be represented as successful browser/API execution.

5. Which engine fits which testing job?

AI TestPilot can remain the orchestration, classification, workflow and reporting layer while specialist engines perform the type of execution they are designed for.

Testing needSuitable engine/toolRole
Browser functional/security-functionalCypress / browser runnerUI workflows, DOM/state assertions, authentication/authorization behavior and safe input validation.
REST/API functional testingAI TestPilot API runnerHTTP requests, responses, status, headers, payload and access-control assertions.
Web/API DASTOWASP ZAPAutomated web application/API dynamic security scanning.
Dependency / SCA and container vulnerability scanningTrivyKnown vulnerabilities in OS/language packages, images and related software components.
SAST / source-code security analysisSemgrep or equivalent SAST engineSecurity rules and vulnerability patterns in source code.
Infrastructure-as-Code / misconfigurationTrivy or dedicated IaC scannerIaC misconfiguration and secret checks.
Load / Stress / Throughputk6, JMeter or equivalent load engineVirtual users, concurrency, throughput, latency and stress behavior.
Accessibilityaxe-core or equivalent accessibility engineAutomated accessibility-rule evaluation in addition to functional accessibility tests.
Network / host vulnerability assessmentDedicated authorized vulnerability scannerHost, service and network vulnerability assessment; outside the normal browser/API engine.
Manual penetration testingAuthorized specialist security-testing toolsetHuman-led penetration assessment under explicit scope and authorization; outside the automation browser/API engine.
Recommended architecture: AI TestPilot should own the test definition, category/subcategory, approval, execution request, normalized findings, evidence, severity, reporting and remediation workflow. The selected specialist engine owns the actual scan/execution and returns structured findings to AI TestPilot.

6. Automation Ready means executable, not guaranteed PASS

Automation Ready means the reviewed case has complete executable actions and verifiable outcomes for its selected engine. It does not mean the application will pass and it does not mean an unsupported specialist scan has been executed.

Do not weaken a requirement to make a test pass. If the requirement is correct and the application violates it, the test should fail and enter the appropriate remediation workflow.

7. FAQ

Can Security tests run in the existing engine?
Yes for security-functional browser/API controls that can be safely and objectively verified, such as authentication, authorization, session behavior, headers, cookies and controlled validation cases.
Does selecting Dependency Vulnerability Scan make Cypress scan packages?
No. The classification can be planned and reported, but package/SCA scanning requires an SCA/vulnerability scanner such as Trivy.
Does Security mean penetration testing?
No. Security is a broad category. Browser/API security-functional testing, DAST, SAST, SCA, infrastructure scanning, network assessment and human penetration testing are different execution disciplines.
Can Load or Stress use normal browser execution?
Not for true concurrency or throughput testing. Use a load engine such as k6 or JMeter.
Does Automation Ready guarantee PASS?
No. It means executable by the applicable engine. PASS/FAIL is determined during execution.
