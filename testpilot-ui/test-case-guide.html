4. Page discovery and dynamic capability matching

TestNexus does not assume that every control supports every assertion. Discovery builds a capability matrix from the application under test.

Discovered exampleApplicable capabilities
<input type="checkbox" data-testid="consent">Checked, Unchecked, Enabled, Disabled, Required, Optional, Visible, Hidden, Exists.
<select data-testid="category">Selected Value, Selected Text, Option Count, Enabled, Disabled, Visible.
<input type="email">Value, Required, Optional, Valid, Invalid, Enabled, Disabled, Visible and discovered field attributes.
<div data-testid="success-panel">Visible, Hidden, Exists, Text, HTML.

Human wording is matched only against discovered elements capable of satisfying the requested intent. Ambiguous evidence stays unresolved rather than being guessed.

5. Cyber-security testing scope

Security scenarios can cover safe, observable controls including Authentication, Authorization/RBAC, Session Management, Input Validation, CSRF-related observable behavior, Security Headers, Cookies, Sensitive Data Exposure, API Security, File Upload validation, Access Control, bounded Rate-Limiting verification, Error/Information Leakage, CORS, TLS/Transport requirements and Logging/Audit evidence where it is accessible.

Execution boundary: Dependency Vulnerability Scan can be classified, planned and reported, but package/SCA scanning is not part of the normal browser/API execution engine. Active exploitation, password spraying, network attacks, port/network vulnerability scanning and destructive penetration testing are also not performed or represented as passed by this engine.

6. Custom testing purposes

Select Custom when your organization uses a testing purpose that is not in the standard taxonomy.

The system interprets these as separate labels:
- Localization
- Data Migration

Custom does not bypass readiness. A Custom test becomes Automation Ready only when its approved steps and outcomes can be grounded to supported application capabilities.

7. Automation Ready means executable, not guaranteed PASS

Automation Ready means the reviewed case has a complete deterministic execution contract with grounded actions and verifiable outcomes. It does not predict whether the application is correct.

Generation and readiness can run concurrently. As each AI-generated case arrives, server-side deterministic readiness is evaluated against the same cached discovery evidence and streamed to the UI. No browser is launched for generation or readiness.

Do not weaken requirements to obtain a PASS. A correct requirement that the application violates should produce a deterministic FAIL during execution.

8. FAQ

Does UI testing mean pixel-perfect screenshot comparison?
No. The current UI category verifies discovered browser elements, content, form/control state, navigation and supported layout/viewport assertions. Do not interpret it as pixel-by-pixel visual regression unless that capability is explicitly implemented.
How does Compatibility work?
Evidence belongs to the browser/environment that actually ran. To claim Chrome + another browser compatibility, execute the same approved suite separately under each configured runtime and compare results.
Can Security tests run?
Yes for safe security-functional browser/API controls that can be objectively observed. The security execution boundary above still applies.
Can Custom values be arbitrary?
They can represent organization-specific testing purposes, but they do not create new automation capabilities. Execution remains constrained to grounded supported actions/assertions.
Does Automation Ready guarantee PASS?
No. Automation Ready means executable. PASS/FAIL is determined only during execution.
